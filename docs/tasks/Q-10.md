# Q-10 — Специфікація П3 «Події вокзалу і видиме комбо» (ADR-035)

**Агент:** game-designer (Sonnet). **Гілка:** task/Q-10-p3-spec. **Доказ:** L0 (документ) + прикидки метрик. Код НЕ писати.

## Контекст
Власник скаржиться, що завдання прості й прямолінійні. П1 (тиск хвилями/цінами) не спрацював (PRESSURE_BASELINE.md). Далі П3 за DESIGN_DEPTH.md: події на вокзалі й видиме комбо.

## Що зробити
Створити docs/design/P3_SPEC.md: 
1. Прочитай DESIGN_DEPTH.md (П3), GAME_DESIGN.md, LEVEL_DESIGN.md, PRESSURE_BASELINE.md (особливо чому експерт встигає всіх), Resources/Config (rules, customers, levels, economy), Core (клієнти/гриль/станції/комбо).
2. Запропонуй 3–5 конкретних подій зміни (напр. автобус з групою клієнтів, зламаний гриль на N секунд, замовлення-«VIP», дощ скорочує терпіння), кожна: тригер, тривалість, вплив на правила (що змінює в Core/конфігах), як гравець реагує, який вибір створює, на яких рівнях з'являється (L03–L10), числа з обґрунтуванням.
3. Видиме комбо: що показати (лічильник/шкала/реакція клієнтів), яка вже наявна логіка комбо/чайових, що це суто UI чи потребує Core.
4. Критерій успіху: ПЕРЕД реалізацією — як виміряти, що подія створює вибір (метрика PressureGapTests розширена: розрив жадібний/розумний >0 для експерта; novice ★ не падає) — прикинь за наявними ботами, які події реально ламають «експерт обслуговує всіх» (потрібне обмеження пропускної здатності або випадкові збої).
5. Розбий на кроки реалізації (картки Q-11…), позначивши: [UI] без рішення Власника / [правила] потребує схвалення Власника / [Core]. Рекомендуй порядок і першу подію.
6. У кінці — 3–5 рядків для Власника простими словами («що змінилось би в грі, що відчує гравець»).
