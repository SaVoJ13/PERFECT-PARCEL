### ADR-001: Затвердження структури AI-команди з 6 агентів та правил Roadmap 1.4
- **Дата:** 2026-11-08
- **Статус:** Accepted
- **Контекст:** Проєкт вимагає високої дисципліни, незалежного контролю якості та чіткого розмежування обов'язків для уникнення хаотичних неконтрольованих змін.
- **Рішення:** Впровадити структуру з 6 спеціалізованих агентів (Agent 0..5), 15 непорушних принципів і строгий цикл затвердження етапів Власником (`Owner Approved`).
- **Наслідки:** Усі зміни проходять через Agent 0 та QA-перевірку Agent 5.

### ADR-002: Модель монетизації: F2P з Rewarded + Interstitial Ads без IAP у MVP
- **Дата:** 2026-11-08
- **Статус:** Accepted
- **Контекст:** Необхідно створити комерційно життєздатну казуальну гру, мінімізуючи технічні ризики платіжних шлюзів на етапі MVP.
- **Рішення:** Затверджено безкоштовну гру з рекламою: Rewarded Ads (подвоєння монет, другий шанс) як пріоритет, та нечасті Interstitial Ads у природних паузах (раз на кілька рівнів). Жодних внутрішньоігрових покупок (IAP) у MVP 1.0.
- **Наслідки:** Немає потреби в інтеграції Google Play Billing API на першому етапі; менше регуляторних ризиків.

### ADR-003: Офлайн-першість (Offline-First) для збереження даних без примусового онлайну
- **Дата:** 2026-11-08
- **Статус:** Accepted
- **Контекст:** Казуальні ігри часто запускаються у дорозі або в умовах нестабільного зв'язку.
- **Рішення:** Увесь ігровий процес 30 рівнів і локальний прогрес працюють без підключення до мережі інтернет. Реклама підвантажується за наявності зв'язку; у разі відсутності зв'язку гра функціонує повноцінно без помилок.
- **Наслідки:** Максимальне утримання користувачів, спрощення бекенд-інфраструктури.

### ADR-004: Заборона автономного редагування `.agents/` без прямої команди Власника
- **Дата:** 2026-11-08
- **Статус:** Accepted
- **Контекст:** Необхідно унеможливити ситуацію, коли AI-агент випадково або навмисно пом'якшує власні обмеження, модифікує правила субординації чи змінює склад команди.
- **Рішення:** Введено незмінну директиву безпеки: будь-якому ШІ суворо заборонено створювати, змінювати або видаляти файли всередині `.agents/` без прямої команди Власника. Директива закріплена в `AGENTS.md`, `.cursorrules` та `.agents/rules/project-governance.md`.
- **Наслідки:** Повний захист системної конфігурації агентів від випадкового перезапису або виходу за межі повноважень.

### ADR-005: Вибір технологічного рушія: Unity 2022.3 LTS (C#)
- **Дата:** 2026-11-08
- **Статус:** **Approved (Офіційно затверджено Власником проєкту)**
- **Ініціатор:** Agent 0 (спільно з Agent 3 та Agent 4)
- **Затвердив:** Власник проєкту (Project Owner)
- **Зафіксований стек:** **Unity 2022.3 LTS (C#)**, .NET Standard 2.1, Target SDK 34+, Android Gradle Plugin, Google Mobile Ads SDK (AdMob) + UMP SDK.
- **Обґрунтування рішення:**
  1. *Максимальна стабільність генерації коду LLM:* Обсяг навчальних даних C# для Unity 2022.3 LTS є найбільшим та найбільш стабільним серед усіх ігрових рушіїв. Це усуває ризик галюцинацій API (на відміну від зламних змін Godot 4.x) та гарантує надійну роботу автономних агентів.
  2. *Зріла підтримка монетизації:* Наявність офіційного Google Mobile Ads SDK для Unity з нативною інтеграцією Google UMP (GDPR) зводить до нуля ризики відхилення білда в Google Play Console або невідповідності Data Safety.
  3. *Автоматизація CI/CD:* Використання перевірених, стабільних Docker-образів Game-CI (`unityci/editor:2022.3.*-android`) для автоматичної безкоштовної збірки APK/AAB через GitHub Actions без необхідності ручної участі Власника.
- **Наслідки:** Уся клієнтська архітектура, скрипти сортування, префаби та системи зберігання проєктуються згідно зі стандартами Unity 2022.3 LTS.

### ADR-008: Корекція монетизаційної моделі: жорсткий дефіцит монет (soft-currency sink), Rewarded Ads та підготовка Google Play Billing (IAP)
- **Дата:** 2026-11-08
- **Статус:** **Approved (Офіційно затверджено Власником проєкту)**
- **Ініціатор:** Власник проєкту (Project Owner) / координатор Agent 0
- **Затвердив:** Власник проєкту (Project Owner)
- **Контекст:** Базова економіка вимагає 54,100 монет для повної прокачки 7 складських покращень. Для забезпечення високого LTV та комерційної рентабельності F2P-моделі необхідно створити органічний стимул до перегляду реклами та мікротранзакцій, унеможлививши легке закриття всіх апгрейдів лише органічним геймплеєм.
- **Зміст рішення:**
  1. *Модель жорсткого дефіциту (Soft-Currency Sink):* Базовий дохід за проходження всіх 30 рівнів обмежується сумою ~8,500–10,000 монет, що покриває не більше 15–20% від вартості всіх покращень складу.
  2. *Основні канали подолання дефіциту:*
     - **Rewarded Ads:** подвоєння нагороди рівня (x2 Win), скриня спонсора (+250 монет) у магазині/меню, другий шанс за рекламу.
     - **In-App Purchases (IAP):** додавання до магазину 3 пакетів монет за реальні гроші (Starter \$0.99, Popular \$2.49, Tycoon \$4.99).
  3. *Архітектурна підготовка Google Play Billing:* Впровадити в `UIManager.cs` інтерфейс магазину з покупкою пакетів монет та переглядом відео за монети, а в `docs/monetization/MONETIZATION.md` зафіксувати інтеграцію Google Play Billing API поряд з Google Mobile Ads (AdMob).
- **Наслідки:** Внесення змін до `ECONOMY_DESIGN.md`, `MONETIZATION.md`, `UIManager.cs` та кодової бази MVP.
