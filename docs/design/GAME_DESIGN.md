# KEBAB STREET — Геймдизайн: правила (Етап 1)

**Автор:** Агент 1 (game-designer). **Статус:** чернетка для E0-10, L0. Основа — `docs/product/GAME_CONCEPT.md` (затверджена). Цей документ лише деталізує її для рівнів 1–5.
**Правило чисел:** усі числа тут — «припущення, перевірити симуляцією» (`tools/economy_sim.py`, бот-тест). Остаточні значення живуть у `Assets/_Project/Resources/Config/*.json`; документ посилається на ключі. Видимі тексти — лише ключі локалізації.
**Жанр:** керування часом. Кожне правило має створювати рішення «що зробити першим».

---

## 1. Цикл зміни
Стани зміни (Core, детермінований такт + seed, `ARCHITECTURE.md` розд. 4):

| Стан | Що відбувається | Вихід |
|---|---|---|
| `Intro` | Показ цілі й порогів зірок (ключі `ui.level.goal.*`), сценка/підказка навчання | тап «Почати» -> `Running` |
| `Running` | Таймер іде, клієнти приходять за розкладом хвиль, станції працюють | час вийшов або ціль-за-клієнтами досягнута й черга порожня -> `Resolving` |
| `Paused` | Пауза гравця (таймер, гриль, терпіння стоять) | -> `Running` |
| `Resolving` | Підрахунок: ціль, зірки, нагороди | `Won` або `Lost` |
| `Won` | Екран результату, зірки, монети, (кристали за 3★ вперше) | далі / повтор |
| `Lost` | Екран «чому програв» (див. 9), опція продовження «+30 секунд» (раз за спробу, на всіх рівнях; `GAME_CONCEPT.md` 5.5, `MONETIZATION_STRATEGY.md` R1) | повтор / продовжити -> `Running` |

Хід зміни: клієнт приходить -> стає в слот прилавка -> гравець збирає страву на дошці з потрібних інгредієнтів -> видає клієнту -> оплата (монети + чайові) -> слот вільний.
Умова дострокового завершення: для цілей «обслужити N» зміна завершується, коли N-й клієнт обслужений.
Тривалість: `level.durationSec` (концепція: 1,5–3 хв; рівні 1–2 коротші).

## 2. Керування (тапи)
Лише тапи, без свайпів (концепція 5.2).
1. Тап по станції (хліб, салат, соус, напій, гриль) — інгредієнт або готове м'ясо йде на дошку.
2. Тап по готовій страві на дошці, потім тап по клієнту — видача.
3. Тап по пригорілому м'ясу — викинути.
4. Черга дій: до `rules.actionQueueMax` тапів запам'ятовуються й виконуються по черзі (припущення). Скасування — тап по елементу в черзі.
Допуск: зона тапу не менша за мінімальний розмір цілі (UI — Агент 2, E0-11).

## 4. Гриль і стан м'яса (фірмова механіка)
Стани шматка м'яса (Core, на такті):

| Стан | Умова переходу | Видимість |
|---|---|---|
| `Empty` (слот порожній) | тап по сирому м'ясу / авто-постачання -> `Raw` | порожній шампур |
| `Raw` | через `grill.cookSec` -> `Done` | рожеве, шипіння |
| `Done` | тап «зрізати» -> м'ясо на дошку; або через `grill.burnAfterDoneSec` -> `Burnt` | зелений індикатор, попереджувальний звук за `grill.warnBeforeBurnSec` |
| `Burnt` | тап -> смітник (штраф `grill.burntPenaltyCoins`) | чорне, дим |

Вхід/вихід: вхід — тап «покласти м'ясо» (скільки слотів вільно); вихід — шматок на дошці (лише зі стану `Done`).
Крайні випадки:
- Взяти `Raw` не можна (дія ігнорується, підказка).
- Пригоріле м'ясо займає слот, поки його не викинули — це створює тиск.
- Пауза заморожує всі таймери гриля.
- Навчальні рівні 1–2: `grill.burnAfterDoneSec` збільшений, пригоріле не дає штрафу монет (параметр рівня `grill.burntPenaltyCoins` = 0, припущення) — поразка не «несправедлива».
Початкові значення: `grill.slots`, `grill.cookSec`, `grill.burnAfterDoneSec` — припущення, перевірити симуляцією та бот-тестом. Слоти постійно поповнюються сирим м'ясом лише тапом (без обмеження запасів у локації 1).

## 5. Рецепти (Етап 1)
Ключі: `recipes.json` -> `recipes[id]`: `id`, `steps[]` (упорядкований список інгредієнтів), `optional[]`, `price`, `unlockLevel`, `nameKey`.

| id | Збирання | Нове на |
|---|---|---|
| `kebab_pita` | піта -> м'ясо -> (салат) -> (соус) | рівень 1 |
Правила збирання на дошці:
- Порядок кроків фіксований за рецептом; хибний інгредієнт можна зняти тапом (без штрафу) або викинути дошку (штраф `rules.boardClearPenaltyCoins`, припущення).
- Необов'язкові інгредієнти (`optional`) додаються, лише якщо їх просить клієнт; зайвий інгредієнт = неправильна страва (клієнт скаржиться, втрата терпіння `rules.wrongDishPatiencePenalty`).
- Ціна страви: `recipes.kebab_pita.price` + надбавка за кожен доданий елемент.

## 6. Клієнти і терпіння
Ключі: `customers.json` -> `customers[id]`: `id`, `patienceSec`, `payMultiplier`, `tipRule`, `special` (одна особливість), `firstLevel`, `nameKey`.

Терпіння: шкала `patienceSec`, відображається сердечками (кількість — `ui.hearts`, відповідність часу: шкала ділиться порівну). Перебіг:
`Arriving` -> `Waiting` (замовлення в бульбашці значками, терпіння спадає) -> `Served` | `Left`.
- Спадання терпіння йде лише в `Waiting`. Клієнт, що пішов (`Left`) — мінус до рейтингу зміни, лічильник `lostCustomers`.
- Вчасна видача: монети за страву + чайові (залежать від залишку терпіння, `tipRule`) + комбо.
- Комбо: `rules.comboWindowSec`; кожна безперервна вдала видача в вікні збільшує множник комбо, помилка/втрата клієнта скидає (припущення).
- Слоти прилавка: `level.counterSlots` (припущення 2–3 на Етап 1); черга за межами слотів чекає й не втрачає терпіння, доки не стане в слот. Це дає гравцю контроль над навантаженням.

Типи на Етап 1 (одна особливість кожен):

| id | Особливість | Перша поява |
|---|---|---|
| `olya` (Студентка Оля) | Терпляча, простий кебаб | рівень 1 |
| `marko` (Таксист Марко) | Мало терпіння, завжди гострий соус, добрі чайові за швидкість | рівень 3 |
| `hanna` (Бабуся Ганна) | Особливе прохання «без цибулі» (поле `request.exclude`) | рівень 4 |

Особливі прохання: клієнт показує значок інгредієнта (закреслена цибуля). Виконано неправильно — як хибна страва. Нові прохання лише за правилом «одна нова особливість на тип».

## 7. Зірки та економіка рівня
Ключі в `levels/Lxx.json`: `goal`, `stars`.
- ★ — ціль виконано.
- ★★ — вищий поріг (`stars.two`, монети або клієнти).
- ★★★ — додаткова умова (`stars.three.condition`: `noLostCustomers` / `noBurnt` / `combo`), за концепцією 5.5.
- Кристали: за 3★ вперше на рівні (економіка — `ECONOMY_DESIGN.md`, поза межами E0-10; нагороди не змінюємо).
- Нагорода монет: сума, зароблена в зміні (`coinsEarned`), переноситься в гаманець; пороги зірок виражені тією самою величиною.

## 8. Бустери (Етап 1)
Бустери в Етапі 1 не входять (перший — рівень 7 за концепцією). Єдина кнопка поведінки — продовження «+30 секунд» (Lost, раз за спробу, без винятків за рівнями). Решта (турбогриль, чай, автонарізка, підмога) — `boosters.json`, Етап 2.
Принцип: кожен рівень проходимий без бустерів (перевіряє бот-тест Агента 3; Агент 1 надає в звіті, чи є запас часу/терпіння).

## 9. Поразка: що бачить гравець
Умова (концепція 5.5): до кінця зміни ціль не виконано. Екран `Lost` показує головну причину (одну), ключі:
- `lost.reason.tooSlow` — мало видано до кінця часу;
- `lost.reason.customersLeft` — пішло забагато клієнтів;
- `lost.reason.burnt` — пригоріло забагато м'яса (рівень з такою умовою);
- `lost.reason.wrongDishes` — багато хибних страв.
Показується також, скільки не вистачило до цілі. Рівні 1–2: умова поразки лише за часом, втрата клієнтів не рахується (захист від несправедливості). Рівень 3: втрата клієнтів рахується (`lose.maxLostCustomers`).

## 12. Питання і суперечності до Агента 0
| № | Питання |
|---|---|
| Q1 | Соуси: концепція вводить рівень 1 «гриль, піта, видача», але Марко (рівень 3) «завжди гострий соус». Пропозиція: соус вводиться на рівні 3 (разом із Марком); салатний бар — рівень 4, як у концепції. Не суперечить концепції, але уточнює порядок. |
| Q2 | Рівні 1–2: ціль «обслужити N» + навчальні параметри гриля (без штрафу за пригоріле). Потребує підтвердження, що це не змінює «умов поразки» (3.2: Власник). Рекомендація: це лише налаштування, не зміна правил. |
| Q3 | Розмір слотів прилавка й `actionQueueMax` — вирішується разом з Агентом 3 у специфікації Core. |
| Q4 | Вибір кінця зміни при досягненні цілі «обслужити N» (дострокове) — підтвердити з Агентом 3. |
