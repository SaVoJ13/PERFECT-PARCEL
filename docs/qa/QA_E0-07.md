## 5. Розбір коду: що перевірено
### 5.1. `SaveService.Load` — BUG-019 (P1)
`SaveService.cs:157-182`, `Inspect`: `catch (Exception)` → `FileKind.Corrupt`. Тобто `IOException`/`UnauthorizedAccessException` під час `ReadText` (файл тимчасово заблокований, помилка носія, права, нестача пам'яті) не відрізняються від пошкодженого тексту. Далі `Load` (`:67-71`, `:84-88`) **перейменовує справний файл у `.corrupt`**. Наслідки (модель, розд. D):
- обидва файли тимчасово не читаються → `NewProfile`, `ProgressReset = true`, `CorruptFilesFound = 2`; файли — лише `save.json.corrupt`, `save.json.bak.corrupt`. Гра (за контрактом) повідомляє «прогрес скинуто», гравець продовжує; після 2 збережень основний і резервний містять новий профіль, справжній прогрес — лише в `.corrupt`, які гра не читає;
- лише основний тимчасово не читається → `Source = Backup` **без** `ProgressReset`: мовчазний відкат на одне збереження; найновіший справний стан відкладено, а наступне пошкодження основного **затирає** його в `save.json.corrupt` (`Quarantine`, `:184-188`, видаляє попередній `.corrupt`).
Те саме в `Save` (`:108`): помилка читання основного → «пошкоджений» → карантин; дані в пам'яті актуальні, тож тут втрати немає, але відкладений справний файл може затерти наступний карантин.
Жоден тест не моделює збій читання під час `Load` (`FaultyStorage` використовується лише в `Save`-тестах).

### 5.2. `SaveService.Save` — помилок не знайдено
Покроково (стан після збою між операціями → що поверне `Load`): запис `.tmp` (частковий) → основний цілий; перевірка → те саме; `Delete(.bak)` → лише основний, `Load` = основний; `Move(основний→.bak)` → `.bak` + `.tmp`, `Load` = `.bak` (= попередній основний); `Move(.tmp→основний)` → новий. Резервна копія ніколи не отримує сміття (пошкоджений основний іде в `.corrupt`, а не в `.bak`) і не отримує старіших даних (у `.bak` завжди потрапляє поточний справний основний). Невдале видалення `.bak` → `IOException` → `Failed`, основний не зачеплено. Лишок `.tmp` ігнорується при завантаженні й перезаписується (`FileMode.Create`). Перевірка після запису читає з носія і порівнює повторну серіалізацію. Перейменування — лише на вільне ім'я (без `File.Replace`). Підтверджено перебором (розд. 4 C).
Обмеження (НЕ ПЕРЕВІРЕНО, як і заявлено виконавцем): `Flush(true)` на Mono/IL2CPP Android і відсутність fsync папки — поведінка при вимкненні живлення лише логічно покрита (будь-яка комбінація імен файлів після збою обробляється `Load`).

### 5.3. Майбутня версія
`Save` перевіряє обидва файли на «новішу версію» до будь-якого запису; `Load` нічого не пише для `NewerVersion`; UI отримує `Source = NewerVersion` і `CanSave = false` (номер знайденої версії в результат не передається — для повідомлення «оновіть гру» достатньо). Зауваження: файл майбутньої версії, який цей розбирач не зможе розібрати (вкладеність > 32, інший синтаксис), вважатиметься пошкодженим і буде відкладений у `.corrupt` (не видалений) — прийнятно, але варто пам'ятати при зміні формату. Невідповідність: основний справний v2 + резервний «новіший» → `CanSave = true`, але кожен `Save` → `RejectedNewerSave` (BUG-023, P3, стан майже недосяжний).

### 5.4. `SaveJson` / `SaveSerializer`
Екранування `"`, `\`, керівних (`\u00XX`) — симетричне; `\uXXXX` і сурогатні пари читаються правильно; переповнення `long` → `double` → «не ціле» → помилка формату; від'ємні значення відхиляються; дробові відхиляються; глибина обмежена 32 (тест на 100 000 `[`); хвіст після документа — помилка; порожній ввід — помилка; культура — `InvariantCulture` скрізь, тест на 4 культурах. Рефлексії й генерації коду немає (безпечно для IL2CPP за читанням коду; на пристрої НЕ ПЕРЕВІРЕНО). Міграція: версія 0, від'ємна, рядок, дробова, відсутня → помилка формату; v1 без `lastSavedUnixSec` → помилка формату.

### 5.5. `TimeGuard` / `IClock`
`EffectiveNow = max`, переповнення неможливе; `DayIndex` правильно округлює вниз для від'ємного часу (тести −1, −86400, −86401); `lastKnownUnixSec` не зменшується ні в `Save`, ні через `Load` (тести). Зауваження: `Save` пише `LastSavedUnixSec` = показ годинника як є; від'ємний показ (годинник до 1970) не проходить власну перевірку схеми → `Save` щоразу `Failed` (BUG-022). Дизайнерський ризик: годинник уперед (напр. помилково на рік) і назад «заморожує» ефективний час, доки справжній час не наздожене (BUG-024, P3, для завдання щоденних нагород).

## 8. НЕ ПЕРЕВІРЕНО
- Файлові операції (`File.Move`, `Flush(true)`, шлях `persistentDataPath`) на Android/IL2CPP — НЕ ПЕРЕВІРЕНО: телефон не в обсязі L2; планується в E0-12 / Етапі 1.
- Безпечність серіалізації під IL2CPP-обрізанням — НЕ ПЕРЕВІРЕНО на збірці з пристроєм; за читанням коду рефлексії немає.
- Поведінка при раптовому вимкненні живлення (довговічність перейменування без fsync папки) — НЕ ПЕРЕВІРЕНО: лише логічний розбір і модель.
- Модель Агента 5 відтворює семантику C# за читанням коду; розбіжності між моделлю і реальним .NET (напр. `double.TryParse` на Mono для `1e400`) можливі в дрібницях, на висновки не впливають.
