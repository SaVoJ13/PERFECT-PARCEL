# Лог кадрів на екрані зміни (S1-22)

Мета: відрізнити задуману затримку дії 0,5 с (ADR-027) від реальних просідань кадрів. Лог є лише в development-збірці; у релізній (`Debug.isDebugBuild == false`) нічого не вмикається.

## 1. Зібрати development-APK
```
gh workflow run build-android.yml --ref <гілка> -f developmentBuild=true
```
Звичайний запуск (без параметра), збірка `main` на push і AAB для Google Play лишаються релізними. APK беремо з артефакту `KebabStreet-Android-Builds` запуску. Підпис збігається зі звичайною збіркою цього запуску.

## 2. Читати лог
Телефон підключено, збірку встановлено, відкрито екран зміни:
```
adb logcat -s Unity | findstr "[KS] frames"
```
Раз на ~5 с реального часу (на паузі гри рядків немає) з'являється рядок:
```
[KS] frames frames=290 avgFps=58.1 maxMs=33.4 over50ms=0
```

| Поле | Значення |
|---|---|
| `frames` | скільки кадрів за інтервал |
| `avgFps` | середня частота кадрів інтервалу (кадри / сума їх тривалостей) |
| `maxMs` | найдовший кадр інтервалу, мс |
| `over50ms` | скільки кадрів довших за 50 мс |

## 3. Як трактувати
- Кадр > 50 мс — відчутне просідання (мікрофриз). `over50ms=0` і `avgFps` близько до частоти екрана — просідань немає, і «затримка» після тапу є задуманою (0,5 с дії, ADR-027).
- Поодинокі `over50ms` одразу після завантаження сцени — нормальні; значущі ті, що повторюються під час гри.
- Якщо `avgFps` низький і `maxMs` великий — просідання реальні, потрібне профілювання.

## 4. Обмеження
НЕ ПЕРЕВІРЕНО на телефоні: у картці S1-22 є лише L2 (логіка і збірка). Реальні числа з пристрою додає той, хто проганяє збірку (L3).
