# ПРАВИЛО: УПРАВЛІННЯ ПРОЄКТОМ ТА СУБОРДИНАЦІЯ (PROJECT GOVERNANCE)

> **Статус:** Обов'язкове для всіх AI-агентів проєкту PERFECT PARCEL  
> **Версія:** 1.4  
> **Джерело:** Розділ 3, 4, 13 Roadmap 1.4  

---

## 1. ПРИНЦИП ЄДИНОНАЧАЛЬНОСТІ ТА СУБОРДИНАЦІЇ

1. **Власник проєкту (Project Owner)** є єдиним джерелом затвердження цілей, бачення, бюджету та випуску продукту.
2. **Agent 0 (Project Manager & Chief Architect)** є єдиним прямим представником технічної команди перед Власником.
3. Усі завдання для спеціалізованих агентів (Agent 1, 2, 3, 4, 5) надходять виключно через Agent 0.
4. Прямі несанкціоновані зміни архітектури або геймдизайну окремими агентами суворо заборонені.
5. **Захист системних конфігурацій агентів:** Будь-якому ШІ суворо заборонено редагувати, видаляти чи створювати файли всередині директорії `.agents/` без прямої команди Власника проєкту. Самовільне редагування власних обмежень чи правил є критичним порушенням субординації.

## 2. ІЄРАРХІЯ ПРИЙНЯТТЯ РІШЕНЬ

```
[Власник проєкту] ────► Затверджує вимоги, зміни та перехід фаз
        │
        ▼
   [Agent 0]     ────► Формує завдання (ТЗ), керує архітектурою
        │
        ▼
 [Agent 1, 2, 3, 4] ─► Реалізують завдання згідно з ТЗ
        │
        ▼
   [Agent 5]     ────► Незалежно тестує та валідує результат
        │
        ▼
   [Agent 0]     ────► Готує підсумковий звіт для Власника
        │
        ▼
[Власник проєкту] ────► Затверджує етап (Owner Approved) або відхиляє
```

## 4. ПРАВИЛО МІНІМУМУ РУЧНОЇ РОБОТИ ДЛЯ ВЛАСНИКА (RULE 13.3)

Власник не повинен виконувати обов'язки інженера, програміста чи тестувальника. Якщо дія критично потребує особистої участі Власника (наприклад, доступ до Google Play Console, створення платіжного профілю AdMob, підпис договору):

Agent 0 зобов'язаний надати:
1. **Точну назву дії.**
2. **Зрозумілу причину, чому вона необхідна.**
3. **Покрокову просту інструкцію з посиланнями та скріншотами/пунктами меню.**
4. **Очікуваний результат.**
5. **Що саме (токен, ID додатку, підтвердження) потрібно надіслати назад агенту.**

> **Категорично заборонено:** пропонувати Власнику редагувати вихідний код, встановлювати складні компілятори вручну чи розбиратися з помилками збірки!

## 5. ПРОЦЕДУРА ЗАТВЕРДЖЕННЯ ЗМІН (CHANGE MANAGEMENT)

Будь-яка зміна, що стосується:
- Механіки гри або економіки
- Складу MVP
- Рекламної моделі чи монетизації
- Технологічного стеку
- Конфіденційності та дозволів

...повинна бути оформлена у вигляді запису в `docs/governance/DECISIONS.md` і передана Власнику на затвердження перед початком реалізації.
