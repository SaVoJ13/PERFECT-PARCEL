## 1. ПРАВИЛО НЕВІДОМИХ ДАНИХ (RULE OF UNKNOWN DATA)

Якщо агент не має достатньої, точної або перевіреної інформації для виконання завдання, він зобов'язаний діяти за алгоритмом:
1. **Чітко виділити невідомі дані** та пояснити, чому вони критичні для проєкту.
2. **Запропонувати технічно обґрунтовані варіанти вирішення** із зазначенням переваг, недоліків та ризиків кожного.
3. **Запросити рішення у Agent 0 / Власника**, якщо питання зачіпає концепцію, бюджет, терміни чи стек.
4. 🚫 **Категорично заборонено вигадувати дані (галюцинувати) або видавати припущення за перевірені технічні факти!**

## 2. ІЄРАРХІЯ АВТОРИТЕТНИХ ДЖЕРЕЛ

При прийнятті технічних та архітектурних рішень агенти спираються виключно на:
1. **Офіційна документація рушія / фреймворку** (Unity Manual, Godot Docs тощо).
2. **Офіційна документація Android Developers & Google Play Console Policy** (актуальні вимоги до Target SDK, Permissions, Google Play Billing, Data Safety).
3. **Офіційна документація Google Mobile Ads (AdMob) SDK & UMP SDK** (впровадження згоди GDPR, формати реклами).
4. **Офіційні відкриті стандарти та ліцензії** (MIT, Apache 2.0, SIL OFL, Creative Commons).

Форуми, неофіційні блоги та застарілі статті (>2 років) можуть розглядатися лише як орієнтир, але вимагають перевірки в офіційних джерелах.

---

## 3. ВАЛІДАЦІЯ СТОРОННІХ БІБЛІОТЕК ТА АССЕТІВ

Перед пропозицією додати будь-яку сторонню залежність або ресурс, агент зобов'язаний перевірити та зафіксувати в документації:
- Точну назву та версію пакету.
- Призначення та необхідність (чому не можна обійтися вбудованими засобами).
- Тип ліцензії (чи дозволяє безкоштовне комерційне використання без копілефту).
- Вплив на розмір збірки (Build Size Impact) та продуктивність.
- Дату останнього оновлення розробниками та активність спільноти.
- Запис у `docs/design/ASSET_REGISTER.md` або `docs/architecture/TECHNICAL_SPEC.md`.
