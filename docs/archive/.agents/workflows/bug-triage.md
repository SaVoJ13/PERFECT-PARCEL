# РОБОЧИЙ ПРОЦЕС: ОБРОБКА ДЕФЕКТІВ ТА ПОШУК ПЕРШОПРИЧИН (BUG TRIAGE & RCA)

> **Призначення:** Стандартизована процедура виявлення, класифікації, усунення та верифікації дефектів  
> **Головна мета:** Усувати причину помилки (Root Cause), а не просто маскувати її прояви, не залучаючи Власника до дебагу.  
> **Джерело:** Розділ 14 Roadmap 1.4  

---

## 1. СХЕМА ОБРОБКИ ПОМИЛКИ

```
┌────────────────────────┐
│ Виявлено дефект        │ (Повідомлення Власника або знайдено QA)
└───────────┬────────────┘
            │
            ▼
┌────────────────────────┐
│ Agent 0: Тріаж         │ Класифікація (P0..P3), призначення розробника
└───────────┬────────────┘
            │
            ▼
┌────────────────────────┐

            │
            ▼
┌────────────────────────┐
│ Виправлення (Agent 3/4)│ Створення fix-гілки та виправлення дефекту

            │
            ▼
┌────────────────────────┐

            │
            ▼
┌────────────────────────┐
│ Закриття & Звіт        │ Фіксація в BUG_REPORT.md, звіт Власнику

```

## 2. КРОКИ РЕАЛІЗАЦІЇ

### Крок 1. Фіксація та тріаж дефекту
- Agent 5 (або Agent 0 при отриманні сигналу від Власника) створює запис у `docs/qa/BUG_REPORT.md`.
- Визначається пріоритет дефекту:
  * **P0 (Блокер):** Робота над новими задачами зупиняється. Вся увага — на фікс.
  * **P1 (Критичний):** Виправляється першочергово в поточному спринті.
  * **P2 / P3:** Планується у чергу завдань.

### Крок 2. Аналіз першопричини (Root Cause Analysis — RCA)
- Розробник (Agent 3 чи 4) зобов'язаний з'ясувати:
  1. *Чому виникла помилка?* (Порушення логіки, стан гонки, витік пам'яті, збій парсингу JSON тощо).
  2. *Чому дефект не було виявлено раніше?* (Прогалина у тестах або специфікації).
- **Суворе правило:** Заборонено просто «гасити» exception або ставити заглушки без розуміння джерела проблеми.

### Крок 3. Виправлення та регресійне тестування
- Створюється гілка `fix/<bug-id>`.
- Вноситься виправлення та додається тест (Unit-тест або новий тест-кейс у `TEST_PLAN.md`).
- Agent 5 проводить тестування:
  1. Перевірка відсутності бага на цільовому пристрої / емуляторі.
  2. Перевірка, що виправлення не зламало сусідній функціонал (регресія).

### Крок 4. Закриття дефекту
- Статус у `docs/qa/BUG_REPORT.md` змінюється на `Closed`.
- Якщо баг повідомляв Власник — Agent 0 надає просте і зрозуміле підтвердження:  
  *«Помилку із сортуванням посилок на 12 рівні виправлено та протестовано на збірці. Причиною був некоректний таймінг спавнера. Тепер усе працює стабільно.»*
