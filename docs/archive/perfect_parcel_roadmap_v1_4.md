## 1. ВІЗІЯ ПРОЄКТУ

### 1.1. Концепція
PERFECT PARCEL — мобільна 2D-гра, у якій гравець керує сортуванням посилок на складському конвеєрі.
Гравець повинен швидко та правильно сортувати посилки відповідно до їхніх характеристик: кольору, напрямку доставки та інших поступово введених параметрів.
За успішне проходження рівнів він отримує ігрову валюту, покращує обладнання, розвиває склад і відкриває складніші рівні.

Гра повинна поєднувати:
- Просту механіку, зрозумілу з перших секунд.
- Поступове збільшення складності.
- Короткі ігрові сесії.
- Відчутний прогрес.
- Приємну візуальну та звукову реакцію на дії гравця.
- Зрозумілу систему винагород.
- Можливість монетизації через рекламу без примусового переривання ігрового процесу.

### 1.2. Основний ігровий цикл
1. Гравець обирає рівень.
2. Починається сортування посилок.
3. Посилки рухаються конвеєром.
4. Гравець направляє їх у правильні сортувальні напрямки.
5. За правильні дії отримує очки та винагороди.
6. Після завершення рівня отримує результат і монети.
7. Витрачає монети на покращення складу.
8. Відкриває нові рівні та механіки.

### 1.3. Продуктові цілі
- Створити завершений ігровий MVP.
- Забезпечити стабільну роботу на цільових Android-пристроях.
- Створити основу для подальшого розширення контенту.
- Інтегрувати рекламну монетизацію.
- Опублікувати гру в Google Play.
- Підготувати архітектуру для майбутніх оновлень.

## 2. ОБСЯГ MVP
MVP повинен бути завершеним продуктом, а не технічним прототипом із мінімальним набором механік.

### 2.1. Функціональність MVP

| Компонент | Обсяг |
| :--- | :--- |
| Ігрові рівні | 30 |
| Типи посилок | 5 |
| Сортувальні напрямки | 3 |
| Локації | 1 склад |
| Ігрова валюта | Монети |
| Покращення | 5–10 |
| Досягнення | 10 |
| Щоденні завдання | 3 типи |
| Локальне збереження | Так |
| Мови | EN / PL / UA |
| Інтернет | Не обов'язковий для основної гри |
| Реєстрація | Не потрібна |
| Хмарна синхронізація | Не входить у MVP |
| Мультиплеєр | Не входить у MVP |
| Внутрішні покупки | Не входять у MVP |

### 2.2. Основні екрани
1. Головне меню.
2. Ігровий екран.
3. Екран результатів рівня.
4. Екран покращення складу.
5. Вибір рівнів.
6. Налаштування.

### 2.3. Вимоги до ігрового процесу
Агент Game Designer повинен визначити та задокументувати:
- Правила сортування.
- Швидкість конвеєра.
- Частоту появи посилок.
- Систему помилок.
- Умови завершення рівня.
- Систему зірок або іншої оцінки.
- Нагороди за проходження.
- Криву складності.
- Баланс економіки.
- Умови розблокування нових рівнів.

*Точні значення не фіксуються до завершення проєктування ігрового балансу.*

### 2.4. Що не входить у MVP
Наступні функції можуть розглядатися після першого релізу:
- Онлайн-мультиплеєр.
- Облікові записи.
- Хмарна синхронізація.
- Система друзів і рейтингів.
- Велика кількість складських локацій.
- Складна система персоналізації.
- Власний внутрішньоігровий магазин із покупками.
- Складна адаптивна система складності.

Жодна з цих функцій не повинна затримувати перший реліз без окремого рішення власника.

## 4. ПРАВИЛА РОБОТИ АГЕНТІВ

### 4.1. Ієрархія рішень
1. Власник проєкту затверджує вимоги.
2. Agent 0 перетворює вимоги на завдання.
3. Спеціалізовані агенти виконують завдання.
4. Agent 0 перевіряє інтеграцію.
5. Agent 5 незалежно перевіряє якість.
6. Agent 0 готує звіт власнику.
7. Власник приймає або відхиляє результат.

### 4.2. Заборона самовільних змін
Агент зобов'язаний отримати погодження, якщо зміна:
- Впливає на ігрову механіку, економіку, структуру MVP, архітектуру, конфіденційність, технологічний стек, терміни або бюджет.
- Додає платні сервіси або змінює рекламну модель.
- Створює нові витрати.

Виправлення локальних помилок у межах затвердженого завдання можна виконувати без окремого погодження, якщо воно не змінює затверджені вимоги.

### 4.3. Формат завдання
Кожне завдання повинно містити: ID завдання, Відповідального агента, Мету, Вхідні дані, Очікуваний результат, Файли, які можуть змінюватися, Критерії приймання, Залежності, Ризики, Необхідні перевірки.

### 4.4. Обов'язковий звіт агента
Після завершення завдання агент звітує:
1. Що зроблено.
2. Які файли створено/змінено.
3. Які рішення прийнято.
4. Які перевірки виконано та їх результати.
5. Що залишилося невиконаним.
6. Виявлені проблеми та ризики.
7. Наступні кроки.

### 4.5. Правило невідомих даних
Якщо агент не має достатньої інформації, він повинен:
- Позначити невідомі дані та пояснити, чому вони важливі.
- Запропонувати варіанти та оцінити наслідки.
- Запросити рішення власника, якщо воно впливає на затверджені вимоги.
- **Заборонено видавати припущення за перевірені факти.**

## 6. ТЕХНОЛОГІЧНА СТРАТЕГІЯ

### 6.1. Вибір технологічного стеку
Технологічний стек не фіксується до завершення Phase 0.
Agent 0 повинен організувати порівняння щонайменше двох придатних варіантів розробки. Unity 2D є одним із кандидатів, але не автоматично затвердженим рішенням.
Порівняння повинно враховувати: продуктивність, простоту, підтримку реклами, можливості AI-агентів, документацію, вартість, ліцензії, створення APK/AAB, складність обслуговування.

### 6.2. Фіксація версій
Після затвердження технологічного стеку потрібно зафіксувати версії: рушія, мови програмування, основних пакетів, Android SDK/NDK, JDK, рекламного SDK, інструментів збірки.
Будь-яке оновлення повинно мати обґрунтування, оцінку ризику та перевірку сумісності.

### 6.3. Контроль залежностей
Для кожної сторонньої бібліотеки або SDK потрібно записувати: Назву, Версію, Призначення, Ліцензію, Джерело, Відомі ризики, Вплив на розмір.
Заборонено додавати непотрібні залежності без технічного обґрунтування.

## 7. GITHUB, РЕЗЕРВНІ КОПІЇ ТА БЕЗПЕКА

### 7.1. Структура роботи з Git
Основна гілка: `main`. Для розробки використовуються окремі робочі гілки.
Правила:
- `main` залишається стабільною; значні зміни туди не вносяться безпосередньо.
- Кожен логічний етап завершується комітом; перед злиттям перевіряються зміни.

### 7.2. CI/CD
Після налаштування середовища необхідно реалізувати автоматичну збірку (APK як GitHub Actions Artifact).
Автоматична публікація в Google Play не дозволяється без окремого затвердження власником.

### 7.3. Секрети та ключі
- API-ключі не зберігаються у відкритому репозиторії.
- Підписні ключі Android захищаються окремо (створюється резервна копія).
- Власник повинен отримати зрозумілу інструкцію щодо дій, які вимагають його особистого доступу або підтвердження.
